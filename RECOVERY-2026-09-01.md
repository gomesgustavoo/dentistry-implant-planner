# The 2026-09-01 data loss, and what was recovered

## What happened

`scripts/pmcanalseg_build_ppc_dataset.py` takes a `--link-into` path and removes
whatever is already there before creating a symlink. It was smoke-tested with
`--link-into ""`. In Python `Path("")` is `Path(".")`, so `shutil.rmtree` ran on the
project root. It deleted every file under `/home/tavulha/dentistry` and only then
failed, on the final `os.rmdir('.')`, with `EINVAL`.

That traceback was visible immediately and was read as a harmless cleanup error.
The bug was patched; **what the failed `rmtree` had already done was not checked.**
`rmtree` deletes contents first and the directory last, so by the time it raised,
the damage was complete. There was no `.git` in that tree.

Two guards existed and neither fired: the script had no "refuse an empty path"
check, and nothing verified the state of the working directory after a destructive
call reported an error. The first is now in the code
(`if str(args.link_into) not in ("", ".")`), with the incident quoted at it.

## What survived

| | why |
|---|---|
| `/mnt/mldata/tf3` — 89 GB | a separate disk the deletion never touched: **all training data, all preprocessed sets, all five trained checkpoints** |
| `dentistry/api:0.10.0` image | `api/` and `dentistry/` as of the last deploy |
| `dentistry/web:0.10.0` image | all of `web/`, including the 4 MB committed `viewer.js` |
| `dentistry/landing:0.10.0` image | all of `landing/` |
| Postgres (in k3s) | every job row and every `reports` blob |
| `/tmp/app.js.bak` | `web/app.js` with the day's plan-tab work |
| `/tmp/worker.env.bak` | every secret and DSN |

Filesystem undelete was attempted and is not viable: ext4 zeroes an inode's block
pointers on unlink, and `debugfs -R lsdel` returned nothing.

## What was rebuilt, and how it was verified

The images turned out to predate the working tree by about six days, so
`dentistry/` came back missing `labels.FOV_LIMITED` and `SINGLE_COMPONENT`,
`metrics.directed_error` / `recall` / `score_comparison` / `challenge_aggregate`,
and `crosswalk.RAW_TO_MERGED_ID` / `merged_vs_toothfairy3_full`. All are restored
and checked against their documented values.

**`worker/` was in no image** -- the worker runs on the host precisely so a ~4 GB
CUDA image never has to be built -- so all 17 modules were rewritten against the
surviving `dentistry/` contracts. That is what makes the reconstruction checkable
rather than a guess: the label space, the crosswalk, the quality checks and the
orientation rules all still exist and all still assert.

Three things prove it rather than suggest it:

1. **`UMambaBot2` loads with `strict=True`.** The architecture was reconstructed
   from the checkpoint's own parameter names, and its Mamba hyperparameters were
   *solved* from the tensor shapes rather than guessed --
   `A_log [8] -> nheads 8`, `conv1d.weight [704,1,4]`, `in_proj.weight [1352,320]`
   give `d_inner 640`, `expand 2`, `headdim 80`, `ngroups 1`, `d_state 32`
   uniquely. A wrong guess fails immediately, and the first one did.
   All four models now load: 47 heads / patch [96,192,256] and 5 heads /
   [80,128,224], mirroring (0,1) throughout.
2. **The phantom suite reproduces its pre-deletion numbers exactly** -- the arch
   fit returns arc 107.6 mm, radius 30.00 against a phantom's 30.0, residual p95
   0.251 mm, s from -54.0 to 53.5; the crosswalk/`to_canonical` commute measures 0
   differing voxels on a non-vacuous 74 295-voxel test.
3. **It caught a real regression in the recovered code.** The image's
   `toothfairy3.fix_raw_header` predates its 2026-08-28 idempotence fix, so
   correcting an already-correct file negated two axes twice -- the defect that
   once republished examples with the mandible above the maxilla. Restored, with
   the guard keyed on the declared orientation code.

`mamba_ssm` is installed without its nvcc extensions (`scripts/patch_mamba_ssm.py`):
`Mamba2Simple`'s scan is a Triton kernel that JITs at runtime, and
`use_mem_eff_path=False` takes the unfused forward, which is the same operation on
the same weights.

**Not rebuilt, deliberately:** the retired three-model arm. Nothing has run it since
the ToothFairy3 model shipped, and reconstructing 400 lines of a path with no users
would be inventing history. Selecting it raises with that said plainly.

## What is genuinely gone

* `data/` -- every job's artifacts. Job rows and reports survive in Postgres, so
  the case list and every report render, but **downloads, 3D views and preview
  tiles 404 for existing jobs**, and the two published examples are gone.
* The downloads: PMCanalSeg (7.9 GB), MMDental (64 GB), the third-party model zips.
  All re-fetchable.
* The clinical test scans `DZ-CBCT`, `Pre/PostDentalSurgery`, `MG_test_scan`,
  `routine_*`. **These may not be re-fetchable and are the one irreplaceable loss.**
* `eval/` -- every measurement file. The numbers survive in the session transcript
  and are being rewritten; the raw `metrics.json` files are not recoverable and the
  runs that produced them would have to be re-run to restore them.
